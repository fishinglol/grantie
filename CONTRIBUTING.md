# Contributing a plugin

Plugins are listed in Granite's **Store** only after a maintainer has read their code. Nothing is installed from an
unreviewed source.

There are two ways in:

- **A plugin of your own** (the normal way): keep it in a GitHub repo of yours and list a reviewed version in the
  [`granite-plugins`](https://github.com/fishinglol/granite-plugins) registry. See below.
- **A change to one of Granite's built-in plugins** (`examples/plugins/<id>/` in this repo): open a pull request here.

## Your own plugin, in your own repo

1. Create a repo with `manifest.json`, `main.js`, a short `README.md`, a licence, and at least 3 real screenshots in
   `screenshots/`. Start from `examples/plugins/hello-granite`; the API is `packages/plugins/src/api.ts` (`GraniteApi`).
   Plain JavaScript that runs as it is: no minifying. (A bundled build is allowed only with its source and a build
   script in the repo, so the reviewer can rebuild it.)
2. Commit, and note the full commit SHA.
3. Fork `granite-plugins`, run `node scripts/registry.mjs pin <owner/name> <sha>`, and open a pull request. CI checks that
   the files at that commit match the hashes; a maintainer reads `main.js` at that commit.
4. To update: raise `version`, commit, and `pin` the new commit in a new pull request. Users get it once it is merged.

The Store pins a commit and the hash of your two files, and the app refuses any file that doesn't match, so changing
your repo without a reviewed entry changes nothing for users. Full guide: <https://granite-docs-phi.vercel.app/guide/publishing>.

## A built-in plugin, in this repo

1. Fork this repo.
2. Add or change a folder in `examples/plugins/<id>/` with `manifest.json`, `main.js`, a short `README.md` and 3 or
   more screenshots. Plain JavaScript that runs as it is: no build step, no minifying, no bundled libraries.
3. Run `npm test --workspace @granite/plugins` (checks the manifest and that the folder name equals the `id`) and
   `npm run check-plugins -w @granite/plugins` (checks it doesn't clash with the other plugins).
4. Open a pull request and fill in the checklist.

Every folder in `examples/plugins/` is bundled into the desktop app when it is built, and the phone's list is
generated by `npm run build:editor` in `apps/mobile`, so a merged change reaches users with the next app release.

## Rules

- `id`: lower-case letters, digits and dashes (for a built-in plugin, equal to the folder name), not used by another plugin.
- Raise `version` whenever `main.js` or the manifest changes, or users never see **Update**.
- Ask only for the `permissions` the plugin really uses, and say why in the README. The risky ones are `network`
  (data can leave the device), `vault.write`, `vault.read`, `editor.style` (CSS applies to the whole app) and
  `editor.input` (the plugin is shown what the user types alone on a line and what they paste).
- Set `"minApiVersion": 2` if the plugin uses `input.trigger` / `input.onPaste` (API 2); older Granite versions then leave it alone.
- Show notes' text with `textContent`, never by building HTML from it.
- It must work on the phone as well as the desktop, or set `"desktopOnly": true`.

## What the reviewer checks

The automated test only checks the manifest's shape. The maintainer reads `main.js` in full and checks that:

- the permissions match what the code does (no `network` unless it needs it; no `vault.write` for a plugin that only reads),
- there is no `eval`, remote script, or use of note text as HTML,
- nothing is hidden: no minified or obfuscated code, no unexplained URLs,
- it does not loop forever (a stuck plugin freezes its own frame) or write to the note in a loop,
- the `id` and `version` follow the rules above.

Plugin authors keep the copyright to their plugin. For a built-in plugin, opening a pull request here means you agree to
license it under this repo's license (see `LICENSE`); a plugin in your own repo keeps whatever licence you gave it.
